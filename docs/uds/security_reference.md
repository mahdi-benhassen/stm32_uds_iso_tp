# SecurityAccess Reference/Test Infrastructure

## Scope and ownership

This document describes the **repository-generated reference/test algorithm** used to exercise the generic UDS SecurityAccess state machine. It is not a reporter-specified production algorithm, an OEM algorithm, or a cryptographic recommendation. Issue #8 identifies the `0x27` callback paths, session restrictions, and lockout behavior, but the supplied screenshots do not define a seed/key formula, secret, byte order, width, rotation, constant, or reference vector.[1]

The generic UDS implementation therefore remains algorithm-agnostic. `library/src/uds.c` accepts application-owned `security_seed` and `security_key` callbacks, performs the session and timing policy, and maps callback results to UDS responses. The reference implementation lives outside the generic library in:

```text
tests/security/uds_security_reference.h
tests/security/uds_security_reference.c
```

An application can replace these callbacks with an approved provider without changing ISO-TP, UDS dispatch, SecurityAccess state handling, or the wire-level level mapping.

> **Warning:** The algorithm in this document is deterministic test infrastructure only. It provides no production security strength and must not protect a real ECU, bootloader, diagnostic service, vehicle function, or secret. Replace it with an independently approved implementation before any product use.

## Repository-generated algorithm

The reference helper supports the two existing wire-level mappings. Both levels intentionally use the same key derivation because Issue #8 does not specify level-specific formulas; the level affects deterministic seed generation only.

| Item | Reference/test rule |
|---|---|
| Supported levels | Level 1 and Level 5 |
| Seed length | Exactly four opaque bytes |
| Key length | Exactly four opaque bytes |
| Seed byte order | Input/output byte 0 first, then byte 1, byte 2, byte 3; no host-endian integer interpretation |
| Test mask | `A5 5A C3 3C` |
| Key derivation | `key[i] = seed[i] XOR mask[i]`, for `i = 0..3` |
| Level 1 wire pair | RequestSeed `0x01`, SendKey `0x02` |
| Level 5 wire pair | RequestSeed `0x09`, SendKey `0x0A` |

For deterministic seed generation, the reference helper starts with the configured 32-bit state, substitutes `0x13579BDF` when the configured state is zero, applies `xorshift32(state XOR level)`, and then applies `xorshift32` four more times. Each seed byte is the most-significant byte of the corresponding resulting state. This rule exists to make host tests repeatable; it is not a security design.

The xorshift operation is:

```text
state ^= state << 13
state ^= state >> 17
state ^= state << 5
if state == 0, use 0xA5A5A5A5
```

All operations are modulo 32 bits. The manual calculator does not generate a seed unless explicitly extended for that purpose; it calculates a key from the four bytes displayed by the ECU.

## Reference vectors

These vectors are **repository-generated**, not supplied by the Issue #8 reporter.

| Level | Seed | Expected key |
|---:|---|---|
| 1 | `00 11 22 33` | `A5 4B E1 0F` |
| 5 | `DE AD BE EF` | `7B F7 7D D3` |

The machine-readable vector record is maintained at `tests/security/reference_vectors.json`. The host contract test also checks deterministic repeatability over 32 generated byte arrays, rejects unsupported levels and wrong seed lengths, and verifies that a one-bit key change is rejected by the reference callback. The UDS integration test exercises both level mappings, seed expiry, invalid-key handling, lockout, session restrictions, reset behavior, and callback replacement at the generic callback boundary.

## Manual calculator

Configure and build the standalone host targets:

```sh
cmake -S library -B build -G Ninja \
  -DUDS_ISO_TP_BUILD_TESTS=ON \
  -DUDS_ISO_TP_BUILD_EXAMPLES=OFF
cmake --build build --target uds_iso_tp_security_test_key
```

Then pass the wire-level security level and the seed as exactly eight hexadecimal digits. The parser reads the seed left-to-right as `seed[0]` through `seed[3]` and accepts an optional `0x` prefix:

```sh
./build/uds_iso_tp_security_test_key 1 00112233
./build/uds_iso_tp_security_test_key 5 DEADBEEF
```

The output includes the selected level, the normalized seed bytes, the calculated key bytes, and a warning that the result is test/reference-only. The utility is implemented in `tools/security_test_key.c` and links to `uds_security_reference_calculate_key()` rather than maintaining a second derivation implementation.

## Manual `0x27` flow

The generic server's default initial security delay is 10,000 ms. After entering Extended (`0x03`) or Programming (`0x02`) session and waiting until that delay has expired, perform the following sequence:

1. Send `27 01` for Level 1 or `27 09` for Level 5.
2. Read the positive response `67 <same-subfunction> <four-seed-bytes>`.
3. Invoke the calculator with level `1` or `5` and the four seed bytes in displayed order.
4. Send `27 02 <four-key-bytes>` for Level 1 or `27 0A <four-key-bytes>` for Level 5.
5. Expect `67 02` or `67 0A` after a valid key.

A key request without a matching pending seed, a key for the wrong level, or a key after seed expiry remains a generic UDS sequence error (`0x24`). A bit-flipped key is reported as invalid (`0x35`), contributes to the generic attempt counter, and can lead to `0x36` and then `0x37` lockout responses. The reference callback does not implement a second timer, session policy, or attempt counter; those responsibilities remain in `library/src/uds.c`.

## Replacing the reference provider

Production integration should provide application-owned functions matching the public callback types in `library/include/uds_iso_tp/uds.h`:

```c
UdsCallbacks callbacks = {
    .security_seed = application_security_seed,
    .security_key = application_security_key,
};
uds_server_init(&server, &callbacks, application_context, now_ms);
```

The production provider must define its approved secret-management, seed generation, key derivation, constant-time verification, failure handling, and lifecycle policy independently. It must also provide test vectors and an ownership/security review. The Issue #8 screenshots alone are insufficient to implement or validate that real algorithm; the reporter must supply the exact formula or an authoritative specification, including seed/key widths, byte order, all constants and transformations, level-specific behavior, secret provisioning rules, and expected vectors.
