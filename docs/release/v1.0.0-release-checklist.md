## Release decision

This checklist supports tagging the current repository tip as **v1.0.0**, provided the tag is understood as a source-available, host-validated engineering release. The implementation has deterministic ISO-TP transport tests, UDS contract tests, adapter contract tests, sanitizer coverage, static-analysis results, and an STM32F767 cross-build. Physical CAN HIL has not been executed in the available environment, so this release must not be described as formally ISO-certified, production-ready, or physically interoperable across all claimed hardware profiles.

The STM32F767 integration is explicitly a **bxCAN/Classical CAN** profile. CAN-FD protocol behavior is implemented and host-tested, with a separate FDCAN adapter contract, but a concrete FDCAN board, transceiver, peer, and captured CAN-FD trace remain required for a physical CAN-FD claim.

|---|---|---|

| Consecutive Frame | IMPLEMENTED and host-tested | Sequence-number generation, wraparound, reassembly, and malformed/sequence-error handling |
| Flow Control | IMPLEMENTED and host-tested | CTS, bounded WAIT, immediate OVERFLOW abort, CAN-ID/DLC/PCI/STmin validation |
| Block Size | IMPLEMENTED and regression-tested | BS=0 is unlimited; BS>0 limits the current CF block; each new CTS replaces BS and resets only the block counter |
| STmin | IMPLEMENTED and regression-tested | Millisecond values are timed on the host clock; `0xF1–0xF9` is accepted with one-millisecond host-resolution approximation |
| Timeouts | IMPLEMENTED and tested | RX/TX deadlines reset on relevant progress and abort expired transfers deterministically |
| Addressing | BOUNDED | Normal configured request/response CAN IDs only; address-extension, mixed, broadcast, and functional policies are out of scope |
| Classical CAN | IMPLEMENTED and F767 cross-built | Maximum 8-byte data field; STM32F767 uses bxCAN |
| CAN FD | IMPLEMENTED and host-tested | Valid data lengths 8/12/16/20/24/32/48/64 bytes; BRS metadata is preserved; physical FDCAN validation is pending |

## 6. Release limitations and follow-up work

The following items are intentionally not represented as completed by this tag:

1. **Physical CAN HIL:** Execute the existing Classical CAN campaign on a real STM32F767 board with a compatible transceiver, two 120-ohm terminations, an independent tester/analyzer, measured timing, and raw timestamped traces.
2. **Physical CAN-FD HIL:** Select and identify a concrete FDCAN-capable STM32 target, configure nominal/data rates and BRS, validate transceiver and message RAM settings, and capture CAN-FD traces.
3. **Formal conformance:** Review the licensed editions of ISO 15765-2 and ISO 14229-1, complete any applicable clause-level review, and do not infer certification from this host evidence.
4. **Product security:** Inject an approved security provider and complete product-specific security, bootloader, Flash, reset, rollback, and recovery validation before any production diagnostic claim.
5. **Timing resolution:** Validate `0xF1–0xF9` STmin behavior with target timers and an analyzer; the host implementation intentionally approximates sub-millisecond values at one-millisecond resolution.
6. **UDS policy:** Complete product-owned DID, session, NRC, programming, and memory-policy review for each target ECU. The release does not claim an unrestricted UDS server or production download implementation.

## 7. Tagging procedure

After confirming the checklist and clean working tree, create an annotated tag pointing exactly to the release commit:

```sh
git fetch origin main --tags
git checkout main
git pull --ff-only origin main
git status --short
git rev-parse HEAD
git tag --list v1.0.0

git tag -a v1.0.0 HEAD \
  -m "Release v1.0.0: host-validated STM32 UDS/ISO-TP engineering baseline"
git push origin v1.0.0

git show --no-patch --format=fuller v1.0.0
git ls-remote --tags origin refs/tags/v1.0.0
```

The tag is valid only if it resolves to the clean release commit selected after the final checks, the tag is annotated, and the push is a normal non-force update. Record the resulting full commit SHA in the GitHub release notes or release evidence. The release remains an engineering baseline until physical validation and product-specific review are complete.
