# STM32C092RC FDCAN integration guide

This guide documents how to integrate the standalone UDS/ISO-TP library into an STM32C092RC CubeMX/Keil project. The repository includes a copy-ready application adapter under this directory, while STM32C092 CubeMX output, the Keil device pack, the FDCAN message-RAM configuration, the linker scatter file, and board transceiver wiring remain project- and board-specific.

## Important memory configuration

The library is hardware-independent and has no STM32 HAL or Keil dependency. Its transport structures contain bounded static payload buffers controlled by `ISOTP_MAX_PAYLOAD`. The default value is 16,384 bytes, which is suitable for larger-memory targets but is too large for a typical STM32C092RC application endpoint in the default configuration.

For a C092 application with 30 KiB SRAM, define an explicit product configuration in the Keil C/C++ preprocessor settings:

```text
ISOTP_MAX_PAYLOAD=4095
```

Do not change the library default globally merely to fit one target. The C092 application must select a bound that fits its endpoint, response buffers, FDCAN objects, stack, and all other static state. At `ISOTP_MAX_PAYLOAD=4095`, the host ABI probe reports `sizeof(UdsIsoTpEndpoint)=12776` bytes. At the default 16,384-byte bound it reports 37,352 bytes, before the application’s other RAM consumers are added.

The 4,095-byte C092 profile preserves normal ISO-TP First-Frame support through 4,095 bytes. The library’s extended First-Frame implementation remains available when a larger target-specific bound is selected.

## Keil/ARM Compiler 6 project settings

The Issue #6 project used µVision 5.41 with ARM Compiler 6.22 (`armclang`/`armlink`), target `STM32C092RCTx`, Cortex-M0+, C99 enabled, optimization level 4, and warning level 3. A compatible project should include the following project-owned sources:

```text
library/src/isotp.c
library/src/endpoint.c
library/src/uds.c
library/src/uds_did.c
library/src/uds_download.c
App/Src/can_transport.c
App/Src/uds_app.c
App/Src/uds_platform.c
```

The maintained C092 adapter equivalents are `can_transport_fdcan.c/.h`, `uds_app_fdcan.c/.h`, `uds_platform_fdcan.c/.h`, and `uds_app_config.h` in this directory. Copy or integrate them into the generated C092 project and retain the generated HAL/FDCAN sources in the application project.

The include paths must contain `library/include`, `library/include/uds_iso_tp`, and the application’s own include directory. The C/C++ preprocessor definitions should include `ISOTP_MAX_PAYLOAD=4095` for the 30 KiB SRAM profile and the MCU/HAL definitions generated by CubeMX. Use C99 or a later ARM Compiler 6 C language mode; the core no longer relies on C11 `_Static_assert` or compound literals for initialization.

The core callbacks use exact function-pointer types declared in the public headers. SecurityAccess is application-owned through `UdsCallbacks.security_seed` and `UdsCallbacks.security_key`; the repository’s deterministic reference helper under `tests/security/` is for host tests and manual experiments only and is not part of this production source list. The application-owned adapter should translate the generated HAL FDCAN headers to and from `IsoTpCanFrame`; no `HAL_FDCAN_*` call belongs in `library/src/isotp.c` or any other core protocol source.

## C092 application profile

The requested C092 Classical CAN profile must explicitly enable serialization padding in the application layer:

```c
isotp_config_classic_can(&config.isotp_config);
isotp_config_set_padding(&config.isotp_config, true, UDS_C092_CLASSIC_PADDING_VALUE);
```

The profile constants are in `uds_app_config.h`; the generic library default remains configurable and disabled. With padding enabled, the serialized Classic CAN frame has DLC 8 and `0xCC` in unused bytes without changing the logical ISO-TP payload length.

For ECUReset, do not treat `HAL_FDCAN_AddMessageToTxFifoQ()` returning `HAL_OK` as physical completion. The maintained adapter sets `FDCAN_STORE_TX_EVENTS`, uses a unique message marker, enables `FDCAN_IT_TX_EVT_FIFO_NEW_DATA`, drains matching `FDCAN_TxEventFifoTypeDef` entries in `uds_c092_fdcan_on_tx_event()`, and exposes `uds_c092_fdcan_tx_complete()` to the generic endpoint. The application calls `uds_isotp_endpoint_tx_complete()` from mainline only after the adapter reports the matching TX event. The reset executor calls `NVIC_SystemReset()` only from the application-owned `uds_platform_fdcan.c` callback.

In the generated C092 application, the copy-ready wiring is:

```c
static UdsC092FdcanTransport uds_transport;

uds_c092_fdcan_transport_init(&uds_transport, &hfdcan1,
                              UDS_C092_REQUEST_ID, UDS_C092_RESPONSE_ID);
uds_c092_app_init_default(&uds_transport, uds_c092_platform_now_ms());

void HAL_FDCAN_TxEventFifoCallback(FDCAN_HandleTypeDef *hfdcan, uint32_t flags) {
    if (hfdcan == &hfdcan1)
        uds_c092_fdcan_on_tx_event(&uds_transport, flags);
}
```

`uds_c092_app_init_default()` is the intended no-manual-declaration profile. It passes `NULL` for the optional application callback table, application context, reset-event callback, and reset-event context. These names are **function parameters**, not global variables or functions. Do not write `&application_callbacks`, `application_context`, `reset_event_callback`, or `reset_event_context` unless the application declares and owns those objects. The equivalent explicit call is:

```c
uds_c092_app_init(&uds_transport, uds_c092_platform_now_ms(),
                  NULL, NULL, NULL, NULL);
```

If the application has its own UDS callbacks or timestamped diagnostics, declare them in an application-owned source/header and pass their addresses explicitly; do not add hidden globals to this adapter.

Enable both notifications in the generated FDCAN startup path, for example:

```c
if (HAL_FDCAN_ActivateNotification(
        &hfdcan1,
        FDCAN_IT_RX_FIFO0_NEW_MESSAGE | FDCAN_IT_TX_EVT_FIFO_NEW_DATA,
        0U) != HAL_OK) {
    Error_Handler();
}
```

The generated `HAL_FDCAN_RxFifo0Callback()` should read the header/data with `HAL_FDCAN_GetRxMessage()`, convert `rx_header.DataLength` with `uds_c092_fdcan_data_length_bytes()`, and call `uds_c092_app_rx_from_isr()` with the identifier, byte length, Classic/FD format, and BRS state. The generated `HAL_FDCAN_TxEventFifoCallback()` should call `uds_c092_fdcan_on_tx_event()` as shown above. Keep both ISRs limited to draining/capturing the frame and setting the bounded handoff; do not run UDS dispatch, Flash operations, reset handling, or waits from the ISR. Mainline code must call `uds_c092_app_process(uds_c092_platform_now_ms())`.

The optional reset-event callback receives `UDS_RESET_EVENT_REQUESTED`, `UDS_RESET_EVENT_RESPONSE_READY`, `UDS_RESET_EVENT_TX_SUBMITTED`, `UDS_RESET_EVENT_TX_COMPLETE`, and `UDS_RESET_EVENT_EXECUTED`. Use it for timestamped diagnostics during HIL only; it is `NULL` and zero-cost at the endpoint boundary when not configured. The adapter’s built-in ECUReset prepare/execute callbacks remain application-owned at the C092 boundary and do not require a separately declared `application_callbacks` object.

## FDCAN adapter requirements

For an STM32C092 FDCAN application, configure the standard IDs required by the application, normally request `0x7E0` and response `0x7E8`, and select `FDCAN_TX_FIFO_OPERATION` for the transmit queue. Route the selected RX FIFO notification to a deferred application path. The adapter must preserve the CAN ID, actual data length, `is_fd` flag, and `bit_rate_switch` flag. HAL data-length enumerations must be translated to the library’s actual byte-length values; they must not be copied as if they were raw DLC codes.

For a Classical CAN profile carried by FDCAN, use `FDCAN_CLASSIC_CAN`, disable BRS, and constrain the data length to at most 8 bytes. For a CAN-FD profile, configure valid data lengths of 8, 12, 16, 20, 24, 32, 48, or 64 bytes and configure nominal/data bit rates and BRS consistently with the independent peer. The FDCAN message RAM, standard filter, RX FIFO, TX FIFO, interrupt routing, and transceiver mode remain board-owned configuration. The supplied C092 profile intentionally uses only the Classic CAN branch; the adapter’s receive decoder handles the C092 HAL’s `FDCAN_DLC_BYTES_0` through `FDCAN_DLC_BYTES_8` values and returns zero for unsupported values.

The ISR should only capture the incoming frame or set the existing pending-frame handoff. It must not run UDS dispatch, Flash operations, reset handling, or blocking waits. Mainline code should invoke the endpoint receive/process/tick functions with a monotonic millisecond clock.

## Required C092 validation

A C092 release claim requires a successful Keil compile and link with warnings reviewed, a map-file memory review, and board validation. The physical campaign should cover Tester Present, Diagnostic Session Control, multi-frame ISO-TP FF/FC/CF, BS, STmin, timeout, and ECU reset. Record the exact MCU, compiler version, firmware SHA, nominal/data bit rates, BRS mode, analyzer identity, raw timestamped CAN trace, and measured inter-frame timing.

This repository currently provides the portable core, the FDCAN adapter contract, a strict freestanding C99 compile gate, and the procedure for completing the C092 integration. It does not claim that the proprietary Keil toolchain or a physical STM32C092 board was executed in the current environment.
